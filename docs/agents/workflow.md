# 代理分工与交付流程

多票、跨模块或需要审查的工作按这里分工。单个会话就能完成的小改动，直接实施并验证，不走审查流程。

## 分工

主控代理负责编排：拆票、写交给实现者和审查者的简报、跑完整套件、读日志、提交、维护 Issue。实际编码和审查交给下面的执行者。

| 工作 | 执行者 |
| --- | --- |
| 跨模块票的设计评审（开工前，只读） | Codex `gpt-6.2-astra`，high |
| 复杂实现：新模块、并发、协议 | Codex `gpt-6.2-astra`，high |
| 每张票的首次完整审查；合入前的 P1 复核 | Codex `gpt-6.2-astra`，high |
| 窄修、按审查意见修复、只改测试、文档 | Claude 子代理（默认 Sonnet，必要时 Opus） |
| 后续轮次审查 | Claude 子代理（Opus） |
| UI 与前端 | Claude 子代理（Opus 或 Sonnet） |

- xhigh 只用于设计，或跨模块的并发问题。
- Codex 在 `.worktrees/<名称>` 工作树中运行。它的 workspace-write 沙箱写不了 `.git`，所以需要运行自检时，用 `--sandbox danger-full-access`，并在简报中写明边界：只在本工作树内修改，不提交、不推送，不注销会话、不结束其他进程、不改系统设置。提交由主控完成。提交说明和 PR 正文都不写任何 AI 署名。
- 简报只给当次任务需要的材料：问题清单、相关文件路径和 [CODING_STANDARDS.md](../../CODING_STANDARDS.md)。不要让执行者通读设计稿和历史审查记录。
- 报告按固定的简短格式写，每个问题一行：级别、现象、位置。详细内容留在文件里。

## 一张票的流程

1. **合入门槛**：开工前写进票里。默认门槛是：没有 P1；P2 只算本票范围内的。观察项不进入修复循环，基线已有的问题转交对应 Issue。
2. **设计评审**：跨模块的票先做设计评审，由用户确认范围后再实现。
3. **实现**：实现者只跑自己改到的自检，`verify.ps1 -Suite <对应套件> -Only <名称>`，跑一次。不带 `-Suite` 时默认是 Gui 套件，其他套件的用例会被跳过。
4. **完整验证**：主控跑一次 `-Suite` 完整验证。标记为 `RequiresFocus` 的用例如果因焦点断言失败，`verify.ps1` 会自动单独重跑一次，以重跑结果为准；其他失败照常算失败。
5. **首次审查**：可以读全仓，以对照基线为准，按 CODING_STANDARDS.md 的审查输出约定报告问题。
6. **后续轮次**：审查者仍可读全仓，但只回答两件事：上一轮的问题是否已修复；这次修复是否在任何地方引入了新问题。不对整票重新做开放式审查。
7. **合入前**：Codex 对整票做一次轻量复核，只报 P1。

## 不收敛时停下

- 只统计修复引入的新问题。问题总数在下降、而且没有修复引入的新问题，就算收敛。
- 审查三轮仍不收敛，停止打补丁，先分析根因，然后**交给用户决定**：重新设计、缩小范围，还是窄修后合入。需要改动已定范围时，同样交给用户决定。
